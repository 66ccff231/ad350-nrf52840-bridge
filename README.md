# 功率计私有协议 → 标准 BLE 功率计 桥接固件（nRF52840）

把功率计的私有蓝牙数据，转成一个**标准 BLE 功率计**广播出去，
让手机 app 与码表当作普通蓝牙功率计连接。

```
功率计 ---BLE 0x2A63---> 本固件（Central） ---BLE 0x1818 CPS---> 手机 app / 码表
```

**目标设备**：行者小G+ 第三代（官方规格：支持 ANT+/蓝牙双连接，功率计均可连）。

## 协议（已全部实测验证）

该功率计通过 **BLE `0x2A63`（Cycling Power Measurement）** 上报，负载 **11 字节**：

| 偏移 | 字段 | 类型 | 验证情况 |
|---|---|---|---|
| 0-1 | 总功率 | u16 LE (W) | ✅ 台架上 1~9 W 时**每帧都满足「总功率 = 左 + 右」**；真实骑行 232 W 峰值下同样成立 |
| 2-3 | 左功率 | s16 LE (W) | ✅ 同上 |
| 4-5 | 右功率 | s16 LE (W) | ✅ 同上 |
| 6-7 | 踏频 | s16 LE (rpm) | ✅ 实测随踩踏 0→64→0，负值（反踩）按协议归零 |
| 8-9 | 曲柄角度 | u16 LE (°) | ✅ 实测连续旋转、0~359 回绕正常 |
| 10 | 错误码 | u8 | ✅ 实测恒为 0 |

**「总功率 = 左 + 右」是字段布局正确的最强证据** —— 实测原始字节：

```
03 00 03 00 00 00 07 00 …   → 总 3 W，左 3，右 0
07 00 00 00 07 00 0f 00 …   → 总 7 W，左 0，右 7
02 00 01 00 01 00 18 00 …   → 总 2 W，左 1，右 1
```

字段定义与 [上游参考实现](https://github.com/DuoDuoJuZi/xds_forwarding)
的 `xds_protocol.c` 一致。若换用其他型号发现字段不符，只需改 `src/xds_protocol.c`。

### 两个容易踩的坑（实测确认）

1. **该功率计的服务 UUID 是非标准的 `0x1828`**
   按蓝牙标准，`0x1828` 是 **Mesh Proxy**，自行车功率服务应为 `0x1818`。
   但实测这台功率计就是在 `0x1828` 服务里放了 `0x2A63` 特征。
   所以本固件**扫描时认 `0x1828`**（也兼容 `0x1818`），**而对外广播用标准的 `0x1818`**。
   这两个 UUID 用途不同，不能混。

2. **不需要向 `0x2A55` 发启动命令**
   上游参考实现会写 `02 16 AA 10` 到控制点，但实测本设备返回 `0x81` 拒绝，
   且不发送也能正常收到测量数据，因此本固件不实现这一步。

## 怎么编译（不需要本地工具链）

用 GitHub Actions 云端编译：

1. 把本仓库推送到 GitHub
2. 推送后 Actions 自动构建
3. 在 Actions 页面下载 artifacts 里的 `xds-bridge-uf2`
4. 得到 `zephyr.uf2`

构建使用 mainline Zephyr `v4.1.0` 与 `boards/others/promicro_nrf52840` 的
`nrf52840/uf2` 目标（该目标带 `CONFIG_BUILD_OUTPUT_UF2` 支持，能直接产出 UF2）。

如果换板子，改 `.github/workflows/build.yml` 里的 `BOARD`：

| 板子 | 板名 |
|---|---|
| ProMicro nRF52840（本项目实测） | `promicro_nrf52840/nrf52840/uf2` |
| Nordic 官方开发板 | `nrf52840dk_nrf52840` |
| Nordic USB Dongle | `nrf52840dongle_nrf52840` |

## 怎么烧录

1. **双击开发板 `RST` 键**，电脑上出现 `NICENANO` U 盘
2. 把 `zephyr.uf2` 拖进去
3. 出现 `0x800701B1 指定不存在的设备` 报错**属正常** —— 引导器写完就重启、
   设备消失，Windows 收尾时就会报这个。U 盘消失即表示烧录成功
4. 判断是否成功：**拔插 USB，若不出现 NICENANO 盘**，说明固件在运行
   （引导器只在无有效固件或你双击 RST 时出现）

## 怎么用

1. 板子用 USB 充电宝供电，放在功率计附近（几米内）
2. **踩一下曲柄**唤醒功率计
3. 板子状态灯（P0.15）：慢闪 = 正在扫描；快闪 = 正在连接；**常亮 = 已连上功率计**
4. 手机/码表里搜蓝牙功率计，认准本固件的广播名（在 `src/main.c` 中定义）

**注意事项**：

- 功率计同时只能被一个设备连接。**用桥之前必须断开手机 app / 码表对功率计本身的连接**，
  否则桥抢不到连接。功率计厂商的官方 app 也要关掉。
- 配对密钥只存在内存里（未启用 `CONFIG_BT_SETTINGS`），**板子断电后需要重新配对**。
  对「骑行期间持续供电」的用法够用。

## 转发了哪些数据

转发负载为 8 字节标准 CPS 格式：

```
flags = 0x0020 (bit5 = 带曲柄数据)
瞬时功率     u16 LE
累计曲柄圈数 u16 LE
上次曲柄事件时间 u16 LE (单位 1/1024 秒)
```

| 功率计数据 | 是否转发 | 说明 |
|---|---|---|
| 总功率 | ✅ 直接转发 | 真实骑行下与官方 app 逐段一致 |
| 踏频 | ✅ 间接转发 | CPS 没有「踏频」字段，转发累计圈数+事件时间，接收端用 `Δ圈数/Δ事件时间` 反推 |
| 左右功率 | ❌ 未转发 | 需要扩展 flags bit0 |
| 曲柄角度 | ❌ 未转发 | CPS 只有「极值角度」，非瞬时角度 |
| 错误码 | ❌ 不转发 | 仅在固件内部用于丢弃异常值 |

**踏频是怎么来的（重要）**：累计圈数是**按踏频积分估算**的，不是功率计实测的累计值
（上游参考实现的作者也在其 README 中说明了同样的问题）。因为接收端是用
`踏频 = Δ圈数 / Δ事件时间` 反推的，所以**事件时间必须和圈数严格一一对应**：
每转满一圈，圈数 +1、事件时间 += 那一圈的周期（`60*1024/rpm`），不能用墙上时钟
匀速推进事件时间。离线验算（整数运算逐位复刻固件逻辑）结果：

| 真实踏频 | 修复后接收端读数 | 修复前（含突发通知抖动） |
|---|---|---|
| 64 rpm | 恒定 64 | 60 ~ 503 rpm，13 帧超 150 |
| 85 rpm | 恒定 85 | 60 ~ 503 rpm，24 帧超 150 |
| 45 / 90 / 120 / 254 rpm | 全部精确相等 | 被量化成 60 或 120 |

剩余偏差只来自整数取整，≤1 rpm。

## 已知限制（如实列出）

1. **行者 app 搜不到本机**。系统蓝牙能看到、其他 BLE 功率计 app 能连，
   但行者 app 的传感器列表不显示。已尝试过：广播标准 `0x1818`、
   加入 Appearance `0x0484`、开启配对、补齐 Feature/Sensor Location 特征 —— 均无效。
   判断为其自身的设备筛选条件所致，非本固件缺陷。

2. **ANT+ 在本硬件上不可行**。需要 Nordic 的 ANT SoftDevice（nRF52840 对应 S340），
   它是预编译固件、需签 Garmin/ANT 许可，且许可限制非 Nordic 原厂芯片。
   更直接的问题是：S340 占用 `0x0~0x305D0`，会**覆盖 UF2 引导器**
   （引导器占 `0x0~0x26000`），因此刷入必须用 SWD 编程器，
   且之后无法再拖拽 UF2 刷机。
   若日后要做 ANT+，建议改用 **nRF52840 Dongle**（Nordic 原厂、USB DFU 刷机、
   不需要 SWD），而不是牺牲这块板子。

3. **左右功率未转发**（见上一节）。

4. **配对密钥不持久化**（见「怎么用」）。

## 修过的 bug（都是实测踩出来的）

| # | 问题 | 症状 | 原因 |
|---|---|---|---|
| 1 | `memcpy(&pending_addr, &info->addr, …)` | **完全连不上功率计** | `info->addr` 是**指针**，这样写等于把指针自身的内存当地址用，连的是垃圾地址 |
| 2 | 对外服务 UUID 用成 `0x1828` | app 搜不到 | `0x1828` 是 Mesh Proxy，标准功率服务是 `0x1818` |
| 3 | 未开启 SMP | 手机「拒绝配对」 | `CONFIG_BT_SMP` 未启用，设备回「不支持配对」 |
| 4 | 断开后未重启广播 | **配对成功后彻底隐身** | Zephyr 的可连接广播在建连后自动停止，且不会自动恢复 |
| 5 | 事件时间按墙上时钟推进 | **踏频乱跳**：Wahoo 平均 60 rpm、峰值 254 rpm（官方 app 同期 0~89 rpm 正常） | 接收端按 `Δ圈数/Δ事件时间` 反推踏频，事件时间却和圈数解耦：每秒圈数是 `1,1,2,1,1,2…` 而事件时间恒 `+1024` → 读数在 60/120 之间跳；又因 `update_crank()` 同时挂在计通知和主循环上，间隔忽长忽短，短窗口落进整圈时读数 = `61440/Δt`，Δt 越小越离谱 → 254 rpm。改为**事件时间只在转满一圈时按该圈周期推进**后，任意通知间隔下的比值都恒等于真实踏频 |

## 排查工具（`tools/`）

需要 `pip install bleak pyserial -i https://pypi.org/simple`。

| 脚本 | 用途 |
|---|---|
| `read_log_auto.py` | **最常用**。自动找到板子的串口并显示固件日志（波特率随意，CDC 不限速） |
| `check_bridge_adv.py` | 扫描并打印板子广播的服务 UUID 与名称，确认广播是否正确 |
| `test_bridge2.py` | 电脑扮演码表连上桥，读取转发的功率数据 |
| `xds_capture.py` | 直连功率计抓原始通知（绕过桥），用于核对协议 |

日志里的关键行：

```
已开始广播「<广播名>」，服务 0x1818（标准功率服务）
扫描到 <地址> rssi -xx dBm 匹配功率计 <<<
已连接功率计
已订阅 0x2A63，开始接收功率数据
收到 总功率=xx W 踏频=xx rpm 左=x 右=x 角度=xx err=0
码表/手机已连接 / 配对完成（bonded=1）
```
